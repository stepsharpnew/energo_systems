## HTTP-сервис заявок

Сервис принимает заявки с сайта и отправляет их на почту через SMTP Mail.ru.

Основной endpoint:

```text
POST /api/lead
```

Обязательные поля JSON:

```json
{
  "type": "service",
  "name": "Имя клиента",
  "contact": "+7 (999)-000-00-00",
  "service": "Название услуги",
  "consent": true,
  "consentVersion": "2026-07-13"
}
```

Дополнительные поля: `email`, `attribution`, `callbackPreferences`. Произвольные поля API не принимает. Для каждой
принятой заявки сервер формирует идентификатор записи и фиксирует версию и
время согласия, IP-адрес, User-Agent и страницу отправки. Лимит — пять попыток
с одного IP-адреса за 15 минут.

### Пожелания к звонку

При указанном телефоне формы передают необязательный объект:

```json
{
  "callbackPreferences": {
    "time": "10:00–18:00",
    "allowNonWorkingDays": false
  }
}
```

`time` — пожелание по московскому времени, до 120 символов без переносов строк.
Пустая строка означает рабочее время 09:00–18:00. `allowNonWorkingDays` — строго
boolean: `true` разрешает звонки в выходные и праздники, `false` означает только
рабочие дни. Это пожелания клиента, а не бронирование звонка.
Оба значения выводятся рядом с телефоном в текстовой и HTML-версиях письма.
Без телефона объект не передаётся. Прежние заявки без объекта также принимаются;
некорректные значения возвращают `400 invalid_callback_preferences`.

### UTM-метки

Все формы передают необязательный объект `attribution`, например:

```json
{
  "attribution": {
    "utm_source": "yandexdirect",
    "utm_medium": "cpc",
    "utm_campaign": "712977221",
    "utm_content": "17786149843",
    "utm_term": "---autotargeting",
    "yclid": "идентификатор-клика"
  }
}
```

Поддерживаемые ключи перечислены в `src/attribution.js`. Значения — строки до
1000 символов без переносов строк; пустые значения пропускаются. Некорректный
объект возвращает `400 invalid_attribution`. Заявки без меток также принимаются.

Метки сохраняются на время вкладки, в том числе при переходах между основным
сайтом и отдельной страницей ИБП. Новая рекламная ссылка заменяет предыдущий
набор меток, чтобы не смешивать кампании. В HTML- и текстовой версиях письма
выводятся строки `utm_source: ...` и остальные переданные поля. Если меток нет,
письмо содержит «UTM-метки: не переданы».

Прямого запроса в CRM этот сервис не делает. Для отдельных UTM-полей в CRM
нужно настроить их заполнение в интеграции, которая обрабатывает эти письма.
Для UTM звонков отдельно проверяются настройки подключённого виджета Novofon
и передачи данных из телефонии в CRM.

При выпуске сначала обновите сервер, затем фронтенд: прежний API отклоняет
новое поле `attribution`, а обновлённый сервер принимает и прежние заявки. Общий браузерный модуль публикуется сборкой Nuxt по адресу
`/scripts/attribution.js`; он нужен также для работы форм страницы ИБП.

### Настройка окружения

При запуске через корневой `docker-compose.yml` переменные должны быть в
корневом `.env` рядом с `docker-compose.yml`:

```env
SMTP_HOST=smtp.mail.ru
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=application@e-systems.su
SMTP_PASS=пароль_для_внешнего_приложения_mail_ru
EMAIL_FROM=Энергосистемы <application@e-systems.su>
EMAIL_TO=sales@e-systems.su
EMAIL_CC=inbox@e-systems.su
ALLOWED_ORIGINS=https://e-systems.su
```

Несколько разрешённых источников можно перечислить через запятую. В рабочей
среде не добавляйте в список посторонние домены.

Для Mail.ru обычно нужен пароль для внешнего приложения, а не основной пароль
от почтового ящика.

### Отдельные отправители ДГУ и ИБП

В корневой `.env` дополнительно внесите пароли приложений с доступом «Только
отправка писем (SMTP)»:

```env
SMTP_DGU_USER=bizdgy@e-systems.su
SMTP_DGU_PASS=пароль_приложения_для_bizdgy
SMTP_UPS_USER=comdgy@e-systems.su
SMTP_UPS_PASS=пароль_приложения_для_comdgy
```

Заявки со страницы `/services/dgu` отправляются через `SMTP_DGU_*`, со страницы
`/services/ups` — через `SMTP_UPS_*`. При отсутствии Referer сервис распознаёт
названия существующих форм «ДГУ — …», «Опрос по ДГУ», «ИБП — …», «Опрос по ИБП»
и опросник «Подбор генератора — резервное питание». В теме появляются метки
`[ДГУ]` или `[ИБП]`, а в теле письма — направление заявки.

Основной получатель у обоих направлений — `EMAIL_TO` (`sales@e-systems.su` по
умолчанию), копии отправляются на адреса из `EMAIL_CC` (`inbox@e-systems.su` по
умолчанию) и дополнительно на `i.lysenko@e-systems.su`. Этот дополнительный адрес
получает только заявки по ДГУ и ИБП, в том числе при отправке через общую учётную
запись. Остальные формы используют прежние
`SMTP_USER`, `SMTP_PASS` и `EMAIL_FROM`. Эти общие настройки нужно сохранить
в рабочем окружении для остальных заявок.

Если оба значения пары `SMTP_DGU_*` или `SMTP_UPS_*` пусты, используется прежняя
общая учётная запись. Если заполнена только часть пары, отправка завершается
ошибкой: пароль другого ящика не подставляется.

При выпуске через GitHub Actions сохраните четыре строки новых настроек
в отдельном секрете `SMTP_LANDING_ENV`. Workflow добавляет его в серверный `.env`
после существующего `DOTENV`, сохраняя общую учётную запись и остальные настройки.
Если новый секрет отсутствует, выпуск работает по прежней схеме.
Локальный `.env` автоматически на сервер не переносится.

### Запуск

```bash
npm install
npm start
```

В Docker сервис слушает порт `3001` внутри compose-сети.

### Проверка отправки

Проверить соединение и авторизацию SMTP без отправки писем:

```bash
docker exec tg_bot npm run check:mail
docker logs --since 2h --tail 200 tg_bot
```

Проверить обе отдельные учётные записи без отправки писем:

```bash
# Локально, из корня проекта (там находится .env):
node tg_bot/src/check-mail.js dgu ups

# На сервере после обновления контейнера и окружения:
docker exec tg_bot npm run check:mail -- dgu ups
```

Проверка выводит используемые адреса отправителей, но не пароли. Каждый ящик
проверяется отдельно; ошибка любого из них даёт ненулевой код завершения.

При успешной отправке лог содержит идентификатор заявки, `messageId` и списки
принятых и отклонённых почтовым сервером адресов. Ответ `{ "ok": true }` означает,
что SMTP принял письмо для основного получателя `EMAIL_TO`. Это не подтверждает
попадание во «Входящие»: фильтры почтового провайдера могут переместить письмо
в спам или прислать уведомление о недоставке на адрес отправителя.

Проверка `/api/health` подтверждает только доступность HTTP-сервиса.

## HTTP-сервис заявок

Сервис принимает заявки с сайта и отправляет их на почту через SMTP Mail.ru.

Основной endpoint:

```text
POST /api/lead
```

Обязательные поля JSON:

```json
{
  "type": "service",
  "name": "Имя клиента",
  "contact": "+7 (999)-000-00-00",
  "service": "Название услуги",
  "consent": true,
  "consentVersion": "2026-07-13"
}
```

Дополнительные поля: `email`, `attribution`. Произвольные поля API не принимает. Для каждой
принятой заявки сервер формирует идентификатор записи и фиксирует версию и
время согласия, IP-адрес, User-Agent и страницу отправки. Лимит — пять попыток
с одного IP-адреса за 15 минут.

### UTM-метки

Все формы передают необязательный объект `attribution`, например:

```json
{
  "attribution": {
    "utm_source": "yandexdirect",
    "utm_medium": "cpc",
    "utm_campaign": "712977221",
    "utm_content": "17786149843",
    "utm_term": "---autotargeting",
    "yclid": "идентификатор-клика"
  }
}
```

Поддерживаемые ключи перечислены в `src/attribution.js`. Значения — строки до
1000 символов без переносов строк; пустые значения пропускаются. Некорректный
объект возвращает `400 invalid_attribution`. Заявки без меток также принимаются.

Метки сохраняются на время вкладки, в том числе при переходах между основным
сайтом и отдельной страницей ИБП. Новая рекламная ссылка заменяет предыдущий
набор меток, чтобы не смешивать кампании. В HTML- и текстовой версиях письма
выводятся строки `utm_source: ...` и остальные переданные поля. Если меток нет,
письмо содержит «UTM-метки: не переданы».

Прямого запроса в CRM этот сервис не делает. Для отдельных UTM-полей в CRM
нужно настроить их заполнение в интеграции, которая обрабатывает эти письма.
Для UTM звонков отдельно проверяются настройки подключённого виджета Novofon
и передачи данных из телефонии в CRM.

При выпуске сначала обновите сервер, затем фронтенд: прежний API отклоняет
новое поле `attribution`, а обновлённый сервер принимает и прежние заявки. Общий браузерный модуль публикуется сборкой Nuxt по адресу
`/scripts/attribution.js`; он нужен также для работы форм страницы ИБП.

### Настройка окружения

При запуске через корневой `docker-compose.yml` переменные должны быть в
корневом `.env` рядом с `docker-compose.yml`:

```env
SMTP_HOST=smtp.mail.ru
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=application@e-systems.su
SMTP_PASS=пароль_для_внешнего_приложения_mail_ru
EMAIL_FROM=Энергосистемы <application@e-systems.su>
EMAIL_TO=sales@e-systems.su
EMAIL_CC=inbox@e-systems.su
ALLOWED_ORIGINS=https://e-systems.su
```

Несколько разрешённых источников можно перечислить через запятую. В рабочей
среде не добавляйте в список посторонние домены.

Для Mail.ru обычно нужен пароль для внешнего приложения, а не основной пароль
от почтового ящика.

### Запуск

```bash
npm install
npm start
```

В Docker сервис слушает порт `3001` внутри compose-сети.

### Проверка отправки

Проверить соединение и авторизацию SMTP без отправки писем:

```bash
docker exec tg_bot npm run check:mail
docker logs --since 2h --tail 200 tg_bot
```

При успешной отправке лог содержит идентификатор заявки, `messageId` и списки
принятых и отклонённых почтовым сервером адресов. Ответ `{ "ok": true }` означает,
что SMTP принял письмо для основного получателя `EMAIL_TO`. Это не подтверждает
попадание во «Входящие»: фильтры почтового провайдера могут переместить письмо
в спам или прислать уведомление о недоставке на адрес отправителя.

Проверка `/api/health` подтверждает только доступность HTTP-сервиса.
